# Аудит производительности и информационной безопасности

Дата аудита: 2026-09-25.

Объект: Sales Performance Dashboard v1, frontend React/Vite, backend .NET 10, PostgreSQL и Docker Compose.

Границы: требования исходного ТЗ и принятые решения v1. Production deployment, авторизация, мобильная версия как обязательный scope и SLA в ТЗ не заданы; риски для production отмечены отдельно.

## Краткий вывод

Для локального v1 критических блокеров не обнаружено. NFR-05 выполнен: расчёты выполняются на сервере, история ограничивается параметром `limit`, запросы используют проекции и `AsNoTracking`, индексы для периода и сортировки созданы, N+1 не обнаружен.

Основные улучшения перед production:

1. уменьшить initial JavaScript bundle или разделить график кодовой загрузкой;
2. включить gzip/Brotli и долгий cache для Vite-ассетов с хешами;
3. убрать фиксированные секреты из репозитория;
4. закрыть или защитить dotnet-monitor, Jaeger и OpenAPI;
5. добавить аутентификацию, rate limiting, TLS и security headers, если API будет доступен за пределами локального окружения.

## Производительность

### Подтверждённые меры

| Проверка | Результат | Свидетельство |
| --- | --- | --- |
| Серверные агрегаты | Пройдена | `AnalyticsService` строит DTO-проекциями и не выгружает продажи целиком |
| Отсутствие N+1 | Пройдена | integration-проверка фиксирует 6 SQL-команд для dashboard на полном seed и выполняет `EXPLAIN (ANALYZE, BUFFERS)` |
| Трекинг EF | Пройден | read-only запросы используют `AsNoTracking()` |
| Ограничение истории | Пройдено | `limit` валидируется в диапазоне 1–100, UI запрашивает 20 строк |
| Индексы | Пройдены | индексы `Sales(SoldAt, Id)` и filtered `Sales(SoldAt, ManagerId)` для `Paid` |
| Отмена запросов | Пройдена | TanStack Query передаёт `AbortSignal` в `fetch` |
| Размер ответа при текущем seed | Приемлемо для v1 | dashboard около 12 KB, sales около 16 KB для 20 строк |

### Найденные риски и улучшения

| ID | Приоритет | Наблюдение | Последствие | Рекомендация |
| --- | --- | --- | --- | --- |
| PERF-01 | P1 перед production | Initial JS bundle: 639 KB исходный размер, около 186 KB gzip; Vite предупреждает о chunk больше 500 KB. Основной тяжёлый компонент — Recharts. | Более медленная первая загрузка на слабой сети и устройстве. | Вынести график в lazy chunk или заменить загрузку библиотеки на более узкую; зафиксировать budget для JS/CSS в CI. |
| PERF-02 | P1 перед production | В `nginx.conf` не настроено gzip/Brotli и нет cache policy для хешированных Vite-ассетов. | Передаётся больше байт, повторные загрузки не используют долгий cache. | Включить gzip/Brotli для JS/CSS/JSON и `Cache-Control: public, max-age=31536000, immutable` для `/assets/*`. |
| PERF-03 | P2 | Один dashboard выполняет 6 последовательных запросов к БД. Для текущего seed это соответствует NFR-05 и проходит планы запросов, но стоимость растёт вместе с объёмом данных. | Латентность будет расти при расширении диапазона и seed. | При появлении SLA измерить p50/p95; затем объединять агрегаты или выполнять независимые чтения через отдельные DbContext только по результатам измерений. |
| PERF-04 | P2 | Для ошибок React Query использует стандартные повторы; при недоступном API пользователь дольше видит loading/error переход. | Лишние запросы при массовом отказе API. | Для 4xx отключить retry, для 5xx ограничить его одной повторной попыткой с backoff. |
| PERF-05 | P2 | В ТЗ нет SLA, performance budget или Lighthouse-порогов. Выполненные замеры — локальный smoke-test, а не нагрузочный бенчмарк. | Нельзя объявить целевые p95 и capacity подтверждёнными. | Перед production согласовать SLA, размер seed, число пользователей и сценарий нагрузки; добавить k6/BenchmarkDotNet/Lighthouse в отдельный этап. |

### Локальные измерения

На запущенном Compose один последовательный запрос через frontend proxy дал:

- `/api/dashboard`: HTTP 200, около 55 мс, 11.98 KB;
- `/api/sales?limit=20`: HTTP 200, около 37 мс, 15.79 KB;
- `/`: HTTP 200; первый запрос после перезапуска контейнера был около 2.1 с, что следует считать cold-start наблюдением, а не SLA.

## Информационная безопасность

### Соответствие ограничениям v1

Отсутствие login/JWT/permissions соответствует явно зафиксированному out-of-scope ТЗ. Порты Compose опубликованы на `127.0.0.1`, backend работает не от root, SQL строится EF Core параметризованными запросами, `ProblemDetails` не отдаёт stack trace или SQL, входные `from/to/rankingBy/limit` валидируются.

### Найденные риски

| ID | Приоритет | Наблюдение | Граница риска | Рекомендация |
| --- | --- | --- | --- | --- |
| SEC-01 | P0 при внешнем доступе | dotnet-monitor запускается с `--no-auth`. | Сейчас порт привязан к loopback; опасно при публикации порта или переносе Compose в общую сеть. | В production удалить `--no-auth`, включить авторизацию/HTTPS или не запускать monitor постоянно. |
| SEC-02 | P1 при внешнем доступе | Jaeger UI и OTLP endpoint публикуются без аутентификации. | Локально доступны только на loopback; на удалённом host это раскрывает трассы и приёмник telemetry. | Не публиковать порты наружу; закрыть сетью/reverse proxy и auth, включить TLS для OTLP. |
| SEC-03 | P1 | `sales_local` находится в `docker-compose.yml` и `appsettings.json`. | Это dev-credential, но он попадёт в историю Git и может быть ошибочно использован вне локального запуска. | Убрать пароль из tracked config, использовать `.env`/Docker secrets/secret manager и отдельного пользователя БД с минимальными правами. |
| SEC-04 | P1 при внешнем доступе | API не имеет authentication/authorization. | Это прямо разрешено scope v1, но любой пользователь с доступом к порту читает всю аналитику. | Перед внешней публикацией добавить identity, роли/read scope и аудит доступа. |
| SEC-05 | P1 перед production | Nginx не задаёт CSP, `X-Content-Type-Options`, `Referrer-Policy`, frame policy и TLS. | В локальном HTTP Compose это ограничение окружения; публичный frontend получает лишнюю поверхность атак. | Добавить security headers на reverse proxy и TLS на внешнем ingress; CSP сначала проверить в report-only режиме. |
| SEC-06 | P2 | Нет rate limiting и явного лимита размера входящих запросов на edge. | Read-only API не принимает тело, а даты и limit ограничены, поэтому текущая поверхность мала; DoS-защита отсутствует. | Внешним ingress добавить rate limiting, connection limits и request timeouts. |
| SEC-07 | P2 | OpenAPI endpoint доступен без защиты. | Удобно для v1 и локальной разработки, но раскрывает контракт API. | В production скрыть или защитить OpenAPI, если контракт не должен быть публичным. |

### Проверенные защитные свойства

- Порты PostgreSQL, backend, frontend, monitor и Jaeger в Compose опубликованы только на `127.0.0.1`.
- Контейнер backend переключается на непривилегированного пользователя `$APP_UID`.
- EF Core использует параметры, а не конкатенацию пользовательского ввода.
- `limit` имеет верхнюю границу 100; выборка продаж ограничена SQL `Take(limit)`.
- Ошибки 500 возвращают безопасное сообщение и trace id; stack trace остаётся в логах.
- `dotnet list package --vulnerable --include-transitive` не обнаружил уязвимых NuGet-пакетов в доступных источниках.
- `npm audit` не завершил проверку: registry advisory endpoint недоступен из текущего окружения. Это не является подтверждением отсутствия уязвимостей npm-зависимостей.

## Решения по результатам аудита

Для текущего локального v1 изменения в коде backend не требуются: обязательные требования ТЗ соблюдены. Следующим техническим шагом рекомендуется выполнить PERF-01/PERF-02 и добавить production security profile отдельным Compose override. SEC-01–SEC-05 становятся обязательными до любого внешнего размещения приложения.
