# Бизнес-правила первой версии

**Статус: принято пользователем 2026-09-25 для v1; реализовано в backend и отображено во frontend.** ТЗ фиксирует базовые формулы, но оставляет часть семантики на выбор разработчика. Связанные решения: D-01–D-09, D-11, D-14. При изменении обновлять этот документ, README, DTO и тесты вместе.

## Деньги и позиции

Принята одна валюта RUB без конвертации, локаль ru-RU. Это согласованное решение для v1. Количество — положительное целое; цена и себестоимость — неотрицательные суммы за единицу в валюте продажи. Разрешить цену ниже себестоимости: убыток не является ошибкой данных. Фиксировать цену/себестоимость в SaleItem на момент продажи, не брать их из текущего Product.

На стороне C# использовать `decimal`, в PostgreSQL — `numeric(18,2)` для цены и себестоимости. Считать на сервере без промежуточного округления агрегатов; деньги в JSON передавать десятичными строками, доли — числами. Агрегаты ограничены диапазоном C# decimal; параметры seed лежат внутри этого диапазона. В read-only API нет ввода пользовательских денежных значений. В UI отображать деньги с двумя знаками; доли преобразовывать в проценты только для представления.

## Статусы и формулы

Принятая модель: Sale имеет текущий статус, возврат полный, история событий и частичные возвраты отсутствуют. В KPI участвуют только продажи `Paid`, попавшие в период по дате продажи.

| Показатель | Правило v1 |
| --- | --- |
| LineRevenue | Quantity × UnitPrice |
| LineCost | Quantity × UnitCost |
| Revenue | Сумма LineRevenue по позициям подходящих Paid-продаж |
| Cost | Сумма LineCost по тем же позициям |
| GrossProfit | Revenue − Cost |
| SalesCount | Число уникальных подходящих Paid-продаж, не число SaleItem |
| AverageCheck | Revenue / SalesCount; при SalesCount = 0 → null |
| Margin | GrossProfit / Revenue; при Revenue = 0 → null |
| Cancelled | Исключена из финансовых агрегатов и SalesCount |
| Refunded | Исключена из финансовых агрегатов и SalesCount, без отрицательного оборота |

Общая маржа — отношение общих сумм, а не среднее арифметическое маржи продаж/менеджеров. Средний чек — отношение общих сумм и количества продаж, а не среднее чеков менеджеров. Пустой период: Revenue/Cost/GrossProfit/SalesCount = 0; Margin/AverageCheck/BestManager = null. Оплаченная продажа с нулевой выручкой учитывается в SalesCount; AverageCheck может быть 0, Margin всё равно null.

Следствие принятого правила возвратов: изменение статуса Paid → Refunded изменяет аналитику исходного периода продажи. Показать отрицательную операцию в периоде возврата невозможно без даты/события возврата. Для тестового seed это допустимый вариант, если явно описать ограничение (§3 ТЗ разрешает выбрать трактовку).

### Контрольный пример для будущих тестов

Paid A: две единицы по 100, себестоимость 60 за единицу; Paid B: одна единица за 300, себестоимость 200. В том же периоде есть Cancelled и Refunded с любыми суммами.

Ожидается: Revenue = 500; Cost = 320; GrossProfit = 180; SalesCount = 2; AverageCheck = 250; Margin = 0.36 (36%). Отменённая и возвращённая продажи не меняют эти результаты. Пример проверяется NUnit unit- и integration-тестами на PostgreSQL.

## Даты и предыдущий период

Хранить время продажи как UTC (`timestamptz`), а календарные границы определять в одной явно заданной business timezone. Timezone машины пользователя не является автоматически timezone бизнеса. Принята зона Europe/Moscow (D-03).

- Пользовательские `from` и `to` — даты `YYYY-MM-DD`, обе включены.
- Backend преобразует их в полуоткрытый интервал `[начало from; начало дня после to)` в UTC.
- Сегодня — текущая бизнес-дата; 7/30 дней — сегодня и предыдущие 6/29 дат.
- Этот месяц — с первого числа по сегодня; прошлый месяц — весь предыдущий календарный месяц.
- Для N календарных дней текущего периода предыдущий — N дней, заканчивающихся за день до `from`.
- Пример: 10–16 сентября включительно → предыдущий 3–9 сентября включительно.
- Calendar arithmetic выполняется до перевода в UTC; день нельзя всегда считать равным 24 часам из-за смены смещения timezone.

Сегодня сравнивается с полным предыдущим днём; текущий день может быть неполным. Это простое правило требует ясной подписи. Сравнение с теми же часами прошлого дня или с предыдущим календарным месяцем — другие варианты D-04.

Процент изменения: `(current − previous) / abs(previous) × 100`, если previous ≠ 0. Если обе величины нулевые — 0%; если previous = 0, current ≠ 0 — null и подпись «нет базы сравнения». Если одна из исходных величин null — изменение null. Изменение маржи показывать в процентных пунктах. Правило для отрицательной прибыли принято в D-04.

## Рейтинг и лучший менеджер

Сортировать по выбранной метрике по убыванию, при равенстве — по стабильному ManagerId по возрастанию. Позиции последовательные, без разделённых мест. Участвуют менеджеры с Paid-продажами в периоде, включая неактивных сейчас. Менеджеры без Paid-продаж остаются видимы отдельными строками «нет продаж», без позиции и без возможности стать лучшим; они не должны обгонять менеджеров с убытком за счёт нулевой прибыли.

Лучший менеджер KPI — первый по GrossProfit независимо от переключателя рейтинга. Если все результаты отрицательные, показать наибольшую прибыль (наименьший убыток) с отрицательным значением. Если участников нет — null. Правила приняты в D-05–D-07 как решения для v1.

## Категории, товары, история

Агрегировать Revenue/GrossProfit по позициям Paid-продаж; top-5 продуктов ранжировать по GrossProfit, затем ProductId. Количество продаж категории — число различных SaleId внутри категории; такая величина **не аддитивна между категориями**, потому что одна продажа может содержать разные категории. Количество единиц товара — отдельная метрика Quantity, её нельзя подписывать как число продаж.

Историю ограничить выбранным периодом, сортировать `SoldAt DESC, Id DESC`, показывать все три статуса. В истории суммы для Cancelled/Refunded — исходная стоимость и расчётная прибыль позиций; явно пометить, что эти строки исключены из KPI. Иначе таблица будет выглядеть противоречащей карточкам. Принятые limit = 20, максимум 100, без обязательной пагинации UI.

## Seed

Принято: 20 менеджеров, 75 клиентов, 6 категорий, 48 товаров, 3 000 продаж за 12 месяцев; фиксированный PRNG seed и версия генератора. Даты задаются относительно параметра anchorDate. При одинаковых seed, anchorDate и версии — одинаковый набор. По умолчанию anchorDate равна бизнес-дате первого запуска, чтобы dashboard был заполнен на актуальном периоде. Это условная, а не абсолютная воспроизводимость; компромисс принят в D-09. Увеличение количества сущностей в 10 раз отменено пользователем.

Повторный старт с той же БД не пересоздаёт продажи и не меняет даты. Нужны сценарии без продаж, равных результатов, граничных дат, крупной сделки, множества мелких продаж и разных маржей. Не полагаться только на вероятность случайного генератора.
