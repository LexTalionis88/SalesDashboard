# Функциональные требования

Источник: PDF в корне, 11 страниц. Статусы приоритета: **MUST** — явно требуется; **SHOULD** — пожелание/ориентир ТЗ; **MAY** — разрешённое дополнение. Все требования пока не реализованы. Правила, которых нет в ТЗ, вынесены в решения D-*: варианты по умолчанию приняты пользователем для v1 2026-09-25. Они дополняют требования источника; статус каждого решения указан в реестре.

## Данные и первичное заполнение

| ID | Приоритет | Требование | Критерий приёмки | Источник |
| --- | --- | --- | --- | --- |
| FR-01 | MUST | Manager: имя, команда/должность, активность, avatar/initials | Данные позволяют показать менеджера и его признаки в UI | §3, с.2 |
| FR-02 | MUST | Customer: имя, компания, сегмент | Продажа связана с клиентом; его данные доступны в истории | §3, с.2 |
| FR-03 | MUST | Category и Product: название товара, категория, необходимые атрибуты | Товар связан с категорией, позиции — с товаром | §3, с.2 |
| FR-04 | MUST | Sale: менеджер, клиент, дата, статус; SaleItem: товар, количество, цена продажи, себестоимость | Продажи поддерживают несколько позиций; хранятся значения для расчёта прибыли | §3, с.3 |
| FR-05 | MUST | Поддержать как минимум Paid, Cancelled, Refunded | Все три статуса представлены и последовательно обрабатываются | §3, с.3; §11, с.8 |
| FR-06 | MUST | Автоматически заполнить БД после первого запуска | После штатного запуска dashboard заполнен, отдельная seed-команда не нужна | §4, с.4; §14, с.8 |
| FR-07 | SHOULD | Объёмы seed: 15–25 менеджеров, 50–100 клиентов, несколько категорий, десятки товаров, 2 000–5 000 продаж | Числа соответствуют ориентирам таблицы ТЗ; конкретные значения фиксируются в D-09 | §4, с.4, таблица «Ориентир» |
| FR-08 | MUST / SHOULD | Данные минимум за 6 месяцев; предпочтительно 12 | Охвачен минимальный период; 12 месяцев — целевой вариант | §4, с.4 |
| FR-09 | MUST | Неравномерные реалистичные данные | Есть сильные/слабые менеджеры, разные чеки и маржа, сезонность, отмены, возвраты, крупные/мелкие сделки, менеджеры без продаж в периоде | §4, с.4 |

## Аналитика и dashboard

| ID | Приоритет | Требование | Критерий приёмки | Источник |
| --- | --- | --- | --- | --- |
| FR-10 | MUST | Рассчитывать Revenue, Gross Profit, Margin, Average Check | Формулы согласованы с §3; единая трактовка статусов и знаменателей во всех блоках | §3, с.3 |
| FR-11 | MUST | KPI: выручка, валовая прибыль, маржинальность, количество продаж, средний чек, лучший менеджер | Шесть показателей для выбранного периода; определение лучшего — D-07 | §5, с.4 |
| FR-12 | MUST | Периоды: сегодня, 7 дней, 30 дней, этот месяц, прошлый месяц, произвольные from/to | Переключение периода обновляет все относящиеся к нему блоки; границы — D-03 | §5, с.4; §11, с.8 |
| FR-13 | MUST | Рейтинг по Gross Profit и Average Check | Доступны два режима серверного ранжирования; равенства и отсутствие продаж обработаны | §5–6, с.4–5; §11, с.8 |
| FR-14 | SHOULD | Детализация рейтинга | Позиция, менеджер, число продаж, выручка, прибыль, средний чек, маржа, изменение к предыдущему периоду | §6, с.5 |
| FR-15 | MUST | Динамика Revenue / Gross Profit / количества продаж | График отражает значения во времени выбранного периода; способ показа и шаг — D-08 | §5, с.4 |
| FR-16 | MUST | Продажи/прибыль по категориям и лучшие продукты | Доступны категориальная аналитика и top продуктов; определение «продаж» и критерия top — D-08 | §5, с.4 |
| FR-17 | MUST | Последние продажи: дата, менеджер, клиент, товары, статус, сумма, валовая прибыль | Таблица содержит перечисленные данные, выдача ограничена; связь с периодом и статусы — D-11 | §5, с.4 |
| FR-18 | SHOULD | Сравнение с предыдущим сопоставимым периодом | Если реализовано, правило периода и изменения описано в README; нулевая база обработана | §5, с.4; §6, с.5 |
| FR-19 | MUST | Основные вычисления и фильтрация на сервере | REST API отдаёт агрегаты; клиент не загружает тысячи продаж для пересчёта dashboard | §7, с.6 |
| FR-20 | MUST | Обрабатывать пограничные случаи | Отмены, возвраты, отсутствие продаж, ничьи, границы дат, крупная сделка, множество мелких сделок, разная себестоимость не искажают результат | §11, с.8 |

## Состояния и дополнительные возможности

| ID | Приоритет | Требование | Критерий приёмки | Источник |
| --- | --- | --- | --- | --- |
| FR-21 | MUST | Initial loading и loading при смене периода | Пользователь видит загрузку; нет бесконечного spinner и смешения данных разных периодов | §10, с.7; последнее уточнение — проект критерия |
| FR-22 | MUST | Ошибка API | Видимое понятное состояние ошибки вместо белого экрана | §7, с.6; §10, с.7 |
| FR-23 | MUST | Пустой период и отсутствие данных отдельного блока | Понятное объяснение в соответствующем месте UI | §10, с.7 |
| FR-24 | MAY | Сравнение менеджеров, sparklines, scatter/bar plots, распределения, доли категорий и другая полезная аналитика | Добавляются только после обязательного объёма; не являются условием минимальной сдачи | §5, с.5 |

CRUD для продаж, клиентов и товаров не запрошен. Минимальные статусы не запрещают расширение, но дополнительные статусы не нужны для исходного объёма. Авторизация и остальные явные исключения перечислены в нефункциональных ограничениях.
